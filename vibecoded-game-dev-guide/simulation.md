## B. Recommended Stack

Simulations are the most architecturally complex genre — they require multiple interacting systems (time, resources, entities, events) that need to stay synchronized. The right stack depends on what kind of simulation:

**City builders / tycoon games:**
- **Godot 4** — scene system handles grid maps, buildings as nodes, population as data. The best engine for complex entity-rich simulations with visual feedback.
- **Single HTML file** — viable for simpler tycoon loops (1–3 resources, no map) but doesn't scale past ~5 systems without becoming unmanageable.

**Life simulations / management:**
- **Single HTML file (JS)** — works well if the simulation is numbers-based rather than spatially-based (like Vibe Code Sim). No rendering complexity.
- **Phaser 3** — good for visual life sims with characters moving around a space.

**Physics-based simulations:**
- **Godot 4** — built-in physics engine handles realistic simulation (e.g., liquid flow, ragdoll, rigid body stacking).
- Avoid building physics simulations in single-file HTML — without a physics engine, you're re-implementing gravity and collision detection from scratch.

**Data persistence:**
- All simulations need save/load. Simulations that run over "days" (in-game) with offline progress especially need reliable state serialization.
- Use JSON save files + localStorage for browser sims.

## C. Prompting Strategy

**The critical first step: define ALL resource types before writing one line of code.** Simulations live or die by their resource graph. If you add resources mid-build, Claude will inconsistently patch them in and create state tracking bugs.

```
Define the complete resource model before any code:

Resources:
- Money: starts at $1,000. Earned from sales, spent on buildings/upgrades.
- Population: starts at 10. Grows when happiness > 60. Max = housing capacity.
- Happiness: 0–100. Affected by parks (+), pollution (-), crime (-).
- Power: generated by power plants, consumed by buildings. Deficit → all buildings offline.
- Housing: capacity provided by residential zones. 1 house = 4 residents.

Buildings (each tile is one building):
- Residential Zone: cost $500, housing +4, pollution +1
- Commercial Zone: cost $800, income +$50/min, happiness +2, pollution +3
- Park: cost $300, happiness +5, no income
- Power Plant: cost $2,000, power +100, pollution +20

Rules:
- Game runs in real-time. 1 real second = 1 in-game hour.
- Population grows by 1 per hour when happiness > 60 and capacity available.
- Money earned: 1 commercial zone = +$50 every 60 seconds.
```

**Build order for city-builder type:**
1. Render a grid (10×10 tiles, each clickable)
2. Click to place one building type (no cost yet)
3. Display the grid with placed buildings visually distinct
4. Add resource panel (money, population displayed)
5. Add building costs (deduct on place, prevent placement if insufficient funds)
6. Add time loop (resource generation ticks every second)
7. Add population/happiness system
8. Add a second building type with different tradeoffs
9. Win/lose conditions

**For time-based simulations (farm, management):**
```
Time system:
- Game clock runs in real-time. 1 real second = 30 in-game minutes.
- Display current in-game time: Day 1, 06:00
- Each crop has a grow_time in in-game hours (e.g., corn = 4 hours = 8 real seconds)
- Time displayed in UI, advances automatically
- "Next Day" button skips to next morning if player wants to fast-forward
```

**Events and random encounters:**
```
Add random events every 2–5 minutes (real-time):
- Market crash: income reduced 50% for 60 seconds
- Population boom: +20 citizens if happiness > 70
- Natural disaster: one random building destroyed (never power plant)
Events show as modal popups with one dismiss button.
Events defined in events.json — never hardcoded in game logic.
```

**For saving/loading:**
```
Implement save/load:
- Save: serialize entire gameState (grid, resources, time, buildings) as JSON
- localStorage key: "sim_save_slot_1"
- Auto-save every 60 seconds
- Load on page open if save exists
- Show "Day X" on load with brief summary: "Loaded: Day 14, $8,432, Pop 127"
```

## D. Common Pitfalls

**Scope explosion.** Simulations are the most dangerous genre for scope creep. "I want a city builder" sounds simple but implies: grid editor, multiple building types, resource generation, population growth, traffic, zoning laws, disasters, campaigns, tutorials... Each feature multiplies the complexity. Start with a single working resource loop before adding any second system.

**Time system inconsistency.** The hardest part of a simulation is keeping time consistent across subsystems. If the crop timer uses `Date.now()`, the factory uses `setInterval`, and the population uses `requestAnimationFrame` — you'll get drift, bugs, and offline progress failures. Define one master game clock:
```
One master tick function runs every 1000ms.
ALL resource updates happen inside this tick function, nowhere else.
Store lastTickTime. On load, calculate missed ticks and apply them.
```

**Save state versioning.** As you add features, your save format changes. Version 1 save files will crash version 2 of the game:
```
Save format: { version: 2, data: {...} }
On load: if save.version !== currentVersion, show "Save incompatible — starting fresh"
Never silently corrupt an old save.
```

**Resource number formatting.** Large numbers appear quickly in simulations. $1,238,490 looks better than $1238490. Ask Claude to add a `formatCurrency(n)` function from the start, and a `formatNumber(n)` for population/production.

**Simulation running while page hidden.** A simulation that ticks in a `setInterval` when the browser tab is hidden can accumulate many hours of "time" while the player is away, producing impossibly large resource counts. Either use the Page Visibility API to pause when hidden and calculate offline progress on return, or deliberately design for offline accumulation (idle-sim style) with a cap.

**Godot memory leaks with many entities.** If your simulation spawns citizens/cars/units as individual nodes, large populations (1,000+) will cause performance issues. Use a data-driven approach: store citizens as dictionary entries, not scene nodes. Only create visual representations for the few entities currently visible.

## E. Kick-off Prompt Template

```
I'm building a simple tycoon management game (browser, single HTML file, vanilla JS).
No libraries. Canvas for the grid, HTML/CSS for the UI panels.

Game concept: You run a small town. Place buildings on a grid to generate income 
and grow your population.

Data model (define in gameData.js):
const BUILDINGS = {
  house:    { name: "House",    cost: 200,  income: 0,   housing: 4, happiness: 1 },
  shop:     { name: "Shop",     cost: 500,  income: 50,  housing: 0, happiness: 2 },
  park:     { name: "Park",     cost: 150,  income: 0,   housing: 0, happiness: 5 }
}

Starting state: $2,000, 10 citizens, 8x8 grid (all empty), happiness: 50

Game rules:
- Click a grid cell to place selected building (deduct cost)
- Can't place on occupied cell
- Income generated: sum of all shop.income every 10 seconds (real time)
- Population grows by 1 every 30 seconds if (housing capacity > current pop) AND (happiness > 40)
- Happiness = avg of all placed buildings' happiness values

First session — build ONLY:
1. 8x8 clickable grid (gray cells, 60px each)
2. Building selector (3 buttons: House, Shop, Park — show cost)
3. Click cell → place selected building (colored rectangle per type)
4. Show resources panel: Money, Population, Happiness
5. Income tick every 10 seconds (shops generate money)

Do NOT add: save/load, events, population growth, tutorials, or win conditions yet.
Confirm the build-and-generate loop works first.
```

## F. Effort & Scope Guide

| Milestone | Time (Hobbyist) |
|---|---|
| Grid + building placement + one resource tick | 2–4 hours |
| 3–5 building types + resource balance | 1–2 days |
| Population/happiness system working | 1–2 days |
| Save/load + events system | 1–2 days |
| Polished release (art, sounds, tutorial) | 2–3 weeks |

**"Done" at MVP:** Place buildings, generate income, population grows, basic win/lose condition (reach population target or go bankrupt).

**"Done" polished:** 8+ building types with upgrade paths, event system, campaign missions, polished UI, sound, mobile-friendly layout.

**The right mindset for simulations:** Build one complete resource loop (place building → generate resource → spend resource → place more buildings) before adding ANY second system. This loop must be fun and bug-free before population, events, disasters, or anything else exists. Simulations that try to add all systems at once always collapse.
